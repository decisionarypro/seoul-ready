## 0. Executive Summary

Seoul Ready는 한국을 처음 방문하거나 준비에 익숙하지 않은 **영어권 해외 여행객**을 위해, 한국 도착에 필요한 선택을 빠르게 정리하고 검증된 외부 사업자의 상품·서비스로 연결하는 여행 준비 큐레이션 플랫폼이다.

고객은 여행 정보가 부족하다기보다 검색 결과가 많고 최신성·적합성을 판단하기 어렵다. 특히 통신(eSIM), 공항 도착, 첫 48시간의 동선, 관광 체험의 예약 여부에서 선택 비용이 발생한다. 서비스는 "정보 나열"보다 **상황에 맞는 결정을 도와주는 신뢰 가능한 가이드**에 집중한다.

수익 모델은 단계적으로 발전한다.

1. **Affiliate:** 승인된 외부 상품으로 방문자를 연결하고 적격 거래에 대한 수수료 수령.
2. **Demand validation:** 고객에게 실제로 선택된 상품·상황·콘텐츠를 추적해 판매력 검증.
3. **Commercial expansion:** 파트너가 허용하는 범위에서 리셀러·API·코브랜딩/화이트라벨 또는 B2B 유통 제휴 검토.
4. **Destination expansion:** 검증된 상품·콘텐츠 템플릿을 부산/제주 및 일본 등 다른 목적지로 확장할 가능성 검증. 초기에는 서울에만 집중한다.

**핵심 원칙:** 사용자의 의사결정 품질이 제휴 커미션보다 우선한다. 제휴 미승인 상태에서 수익 발생을 암시하지 않으며, 현지 최신성·가격·정책은 검증 시점을 공개한다.

## 1. 사업 배경 및 기회

### 1.1 문제 정의

- 여행객은 한국 현지 통신 수단을 구매하기 전 기기 eSIM 지원, 통신사 잠금 해제, 데이터 사용량, 전화번호 제공 여부를 별도로 조사해야 한다.
- 공항에 도착한 뒤 이동 방식과 숙소까지의 동선이 불확실하면 불안과 불필요한 지출이 발생할 수 있다.
- 체험 상품은 업체별 예약 조건·취소 규정·출발 장소·운영 날짜가 다르며 선택 과정에서 비교 비용이 크다.
- 많은 여행 콘텐츠가 홍보성 문구 중심이거나 작성일이 오래되어, 여행자가 믿을 수 있는 기준을 확인하기 어렵다.
- 기존 종합 OTA는 예약·재고·가격 제시에는 강하지만 여행 전 준비 단계의 조언과 선택 도우미 경험은 제공 범위가 서로 다르다. 이 차별화 가설은 실제 사용자 검증이 필요하다.

### 1.2 핵심 인사이트와 사업 가설

| ID | 가설 | 검증 방식 | 반증/실패 신호 |
|---|---|---|---|
| H01 | 입국 준비 맥락에 맞는 가이드가 일반 상품 나열보다 더 많은 적격 구매 클릭을 만든다 | 의도별 랜딩 A/B 또는 순차 실험 | 가이드 열람자는 많으나 적격 구매 행동이 거의 없음 |
| H02 | 통신 연결은 여행 전 필수 결정이라 초기 구매 전환 신호를 만들 수 있다 | eSIM 가이드→공식/제휴 클릭→공급사 승인 거래 | 제품 클릭 대비 구매 발생이 현저히 낮음 |
| H03 | 첫 48시간 체험 큐레이션은 여행 맥락 기반 교차 판매에 기여한다 | 가이드별 클릭 및 공급사 매출 매핑 | 방문·스크롤만 높고 구매 클릭이 없음 |
| H04 | 영문 검색 콘텐츠는 반복적·저비용 구매 의도 트래픽을 생성할 수 있다 | 인덱싱·유입검색어·비브랜드 클릭 | 충분한 품질 개선 후에도 검색 노출 미미 |
| H05 | 한국 현지에 대한 구체적이고 정확한 설명이 신뢰와 클릭을 높인다 | 사용성 테스트·피드백·비교 실험 | 추천 이유와 조건을 이해하지 못함 |
| H06 | 제휴 판매량이 쌓이면 직접 리셀러/코브랜딩 협상이 경제적일 수 있다 | 환불·수수료·매입마진·CS원가 추산 | 자체 판매 추가 비용이 예상 마진 초과 |

**원칙:** 제휴사 이름을 늘리는 것과 사업을 검증하는 것은 다르다. 구매 의도, 클릭, 최종 승인 수수료, 현금 정산까지 모두 봐야 한다.

### 1.3 경쟁 및 대체재

- **직접 대안:** Airalo·Saily 등 통신사/서비스 제공사의 직접 판매 사이트.
- **간접 대안:** Klook·Viator·Expedia·여행 OTA와 현지 가이드.
- **콘텐츠 대안:** 여행 블로그, YouTube, Reddit, 공식 관광기관 자료, AI 기반 검색 답변.
- **우리 차별화의 출발점:** 처음 방문하는 영어권 고객의 "도착 전 의사결정 순서"에 맞춰 비교하고 공식 조건 확인 방법을 제시한다.
- **위험:** 무료 AI 답변과 대형 OTA 콘텐츠가 유사한 정보를 제공할 수 있다. 복제하기 어려운 현지 검증, 구체적 의사결정 규칙, 신뢰도, 누적 콘텐츠 운영력이 필요하다.

## 2. 목표, 비목표, 성공 정의

### 2.1 1차 목표 (0~30일)

1. 안정적으로 접속 가능한 반응형 영문 사이트 공개 및 검색엔진 인덱싱 준비.
2. 적합한 제휴 프로그램 최소 2개 신청, 승인 및 정산 가능 국가/계정 조건 확인.
3. 가격·호환성·취소정책 등 핵심 정보의 정확성 QA 통과.
4. 구매 의도 기반 영문 가이드 4~6개로 확장 및 콘텐츠 배포 채널 2개 테스트.
5. 추적 동의·준법 검토 후 최소한의 측정 체계 마련.
6. 첫 **적격 구매 또는 명확한 구매 의도 신호** 확인. 실제 입금은 공급사의 정산 주기와 고객 이용 완료에 의존한다.

### 2.2 2차 목표 (31~90일)

- 의도별 유입 채널과 상품별 예상 공헌이익을 계산할 수 있는 수준의 데이터 확보.
- 2개 이상의 상품군에서 반복 클릭·전환 여부 확인.
- 클릭만 유발하고 구매가 발생하지 않는 콘텐츠 개선 또는 중단.
- 승인된 거래·취소·유효 커미션·입금 데이터를 서로 구분한 수익 리포트 운영.
- 조건이 허용되는 공급사를 대상으로 리셀러/API 제휴 경제성 비교.

### 2.3 비목표(초기 범위 제외)

- 자체 항공권·숙박·투어 재고 확보 및 예약 관리.
- 자체 결제, 카드 정보 수집, 환불 처리, 자체 상품 공급 책임.
- 실시간 재고나 가격 보장.
- 개인별 행동 데이터 판매, 사용자 위치 추적.
- 자동 수집/무단 스크래핑을 통한 대규모 데이터 복제.
- 관광 상품의 허위 후기·사용 경험 작성.
- 한국어 국내 여행객 전면 공략 또는 전 세계 여행 국가 동시 확장.
- systeme.io 등 B2B SaaS를 서울 여행객용 동일 페이지에 노출하는 것.

### 2.4 North Star Metric

**월간 적격 제휴 구매 건수(Valid Referred Purchases, VRP)**

정의: 방문자가 본 사이트의 승인된 추적 링크를 통해 구매했고, 공급사의 검증을 통과한 거래 수. 취소·환불·무효 거래는 제외한다. 이 수치가 확인되지 않는 공급사에서는 잠정 구매와 확정 구매를 별도 표기한다.

보조지표: 상품별 지급 확정 수수료(USD), 유입 1,000세션당 확정 수수료(EPC/1K), 실제 입금액, 콘텐츠별 기여도.

## 3. 타깃 고객과 JTBD

### 3.1 핵심 페르소나 P1 — 첫 한국 여행 영어권 자유여행객

- **상황:** 3~7일 서울 여행을 예약했고, 출발 2주 전부터 준비한다.
- **해야 할 일(JTBD):** 도착 후 통신과 이동에 실패하지 않고 첫 일정의 불확실성을 제거하고 싶다.
- **불편:** eSIM/SIM, 데이터량, 공항 이동, 예약 필요 체험의 선택 기준을 모르거나 시간이 부족하다.
- **성공:** 5~10분 이내 실용적인 체크리스트와 적합한 공식 구매 경로를 얻음.
- **행동:** 검색, 영상 조회, 여행 커뮤니티 질문, 가격 비교.

### 3.2 P2 — 짧은 체류/환승/비즈니스 방문객

- **상황:** 1~3일 체류, 준비 시간이 부족함.
- **목표:** 통신·공항 이동을 최소 시간에 해결하고 확실한 일정 하나만 예약.
- **가치:** 복잡한 선택지를 줄이는 단순 가이드, 짧은 체류 옵션, 지출/실패 리스크 설명.

### 3.3 P3 — 7일 이상 장기 체류객

- **상황:** 1~4주 이상 체류.
- **목표:** 데이터 사용량, 국내 번호 필요 여부, 장기 통신 요금, 체험 스케줄을 잘 선택.
- **가치:** eSIM과 국내 통신사 상품 차이, 조건별 판단 기준, 일정 유연성.

### 3.4 제외/후순위 페르소나

- 한국 거주 현지인 및 한국어 여행 정보 소비자.
- 단체여행 전용 B2B 운영사.
- 당장 자체 예약/결제·CS를 요구하는 고객.
- 온라인 창업/마케팅 SaaS 고객: 별도 마이크로 브랜드로 분리.

### 3.5 사용자 핵심 질문

1. 내 기기는 한국용 eSIM을 쓸 수 있는가?
2. 며칠 동안 데이터가 얼마나 필요한가?
3. 데이터 전용 eSIM으로 한국 전화번호나 SMS 인증이 가능한가?
4. 공항에서 숙소까지는 무엇이 가장 간단한가?
5. 서울 첫 48시간에 무엇을 미리 예약해야 하는가?
6. 추천 근거, 비용 차이, 취소 가능 여부는 어디서 확인하는가?

## 4. 고객 여정 / 서비스 플로우

### 4.1 기본 흐름

`검색/영상/커뮤니티 → 관련 가이드 또는 홈 → 사용 조건 확인 → 추천 설명 → 공식/승인 제휴 링크 → 공급사 사이트 구매 → 공급사 거래 검증 → 수수료 확정 → 지급`

사이트는 공급사 결제 후의 사용자 화면과 계정 데이터에 직접 접근하지 않는다. 서버 간 콜백/API를 도입하지 않는 한 전환은 파트너 대시보드 집계 또는 승인된 리포트로 확인한다.

### 4.2 진입별 흐름

- **eSIM 검색 유입:** eSIM 가이드 직행 → 호환성·전화번호·데이터 체크 → 공급사 옵션 → 제휴 링크.
- **서울 일정 유입:** 첫 48시간 가이드 → 여행 목적별 체험 선택 → Viator/기타 승인 공급사.
- **홈 유입:** 핵심 가치 → 2질문 플래너 → 해당 가이드·체험 링크 → 공급사.
- **모바일 메뉴:** 핵심 섹션 이동 → 읽기 → 외부 구매 링크.

### 4.3 에러/예외

- 공급사 미승인: 공식 비제휴 URL로 연결하고 수익·파트너십 주장 금지.
- 잘못된 제휴 URL: 표시하지 않고 검증된 공식 URL로 대체. HTTPS만 허용.
- 구매 링크가 국가·언어 문제로 열리지 않음: 구매 국가·브라우저·추적 제한 점검, 일반 공식 링크 제공.
- 데이터 연결 없음: 읽기 가능한 정적 페이지 자체는 캐시 가능한 구조로 유지하되 오프라인 보장은 하지 않음.
- 여행 플래너 값 누락: 기본값의 사용 여부를 UI로 명확하게 안내하거나 필수 선택 검증.
- 공급사 가격 변경: 고정 가격 표시 제거 또는 검증일과 조건부 안내, 공식 가격 확인으로 유도.
- eSIM 미지원/기기 잠금: 구매 추천보다 호환성 확인과 물리 SIM 대안 안내.
- 공급사 상품 품절/운영 중단: 해당 링크 비활성화 또는 검증된 대안 제공.

## 5. 기능 요구사항

우선순위 표기: **P0 = 출시 필수**, **P1 = 효과 검증 단계**, **P2 = 확장 단계**. 상태: 구현/부분 구현/미구현.

### 5.1 FR-01 홈/랜딩 (P0, 구현)

- 영문으로 제품 가치, 대상 사용자, 핵심 서비스의 범위를 1화면 내 전달.
- CTA: Trip Planner / eSIM Guide / Explore Seoul / First 48 Hours.
- 현재 사용자가 구매·예약하지 않는다는 점을 명확히 표시.
- 이동 시 자사 도메인 내 페이지와 공급사 외부 링크를 구분할 수 있어야 함.
- 광고·제휴 관계를 고지 페이지로 연결.
- 검색 엔진용 페이지 제목·설명·Open Graph 태그 포함.
- **완료 기준:** 모바일 360px와 데스크톱 1440px에서 가로 스크롤·핵심 CTA 누락이 없고 모든 내부 링크 동작.

### 5.2 FR-02 2질문 여행 플래너 (P0, 구현)

**입력값**
- 기간: `short`, `medium`, `long` (기존 구현의 세 범주; 실제 일수 설명은 명확화 필요).
- 관심사: `food`, `culture`, `highlights`.

**처리**
- 3×3 조합에 맞춰 여행 톤, 핵심 제안, 기본 도착 체크리스트 노출.
- 사용자 식별 없이 브라우저 내에서 즉시 결과 생성.
- 결과 수정(Edit plan) 시 이전 질문 페이지로 복귀.
- 위험한 추정이나 개인화된 확정 예약 가능성을 암시하지 않음.

**범위 제한**
- 현재는 추천 알고리즘이나 실시간 인벤토리 매칭이 아닌 규칙 기반 편집 콘텐츠.
- 입력값은 서버에 저장되지 않음.
- 기간·관심사가 실제 구매 의도와 연결되는지는 테스트 필요.

**개선 요건(P1)**
- '1~3일 / 4~7일 / 8일 이상' 등 이용자가 이해할 명시적 기간.
- 추천 결과에서 설명 근거 및 관련 가이드·상품 연결.
- 초기 질문 수 증가 전 이탈률 검증.
- 이용자에게 결과 복사/공유 기능 선택적으로 제공.

**인수 기준**
- 9개 조합 전체에서 빈 화면/JS 에러 없음.
- 키보드만으로 입력·결과·수정 가능.
- 다른 입력 조합 간 결과 일관성 및 설명의 안전성 검증.

### 5.3 FR-03 eSIM 선택 가이드 (P0, 구현)

필수 콘텐츠:
1. 통신사 잠금 해제 및 eSIM 호환 기기 확인.
2. 데이터 전용 상품과 음성통화/SMS/한국 번호 제공 상품 구분.
3. 예상 데이터 사용량 판단 방법(절대 수치를 과도하게 단정하지 않음).
4. 설치 시점·개통/활성화 유의사항.
5. 비교 기준: 지원 망, 데이터량, 이용 일수, 속도 제한, 테더링, 환불/교환, 고객지원.
6. 공식 공급사 링크, 검증일, 광고 고지.
7. 적합하지 않은 고객에게 물리 SIM 또는 공식 통신사 대안 제공.

**인수 기준:** eSIM 미지원 단말 보유자도 구매를 서두르지 않고 대안을 찾을 수 있어야 한다.

### 5.4 FR-04 첫 48시간 가이드 (P0, 구현)

- 공항 도착 → 통신 → 이동수단 → 숙소 체크인 → 부담 적은 첫 일정 순서 제공.
- 교통 정보는 공식 소스나 운영사 공지에 기반해 업데이트.
- 관광 체험은 사용자의 체류 기간/관심사와 맞는 설명 및 예약 필요성 판단 기준 제공.
- 체험 판매 상세페이지의 실제 운영 일자·취소 규정·포함/미포함 사항은 공급사에서 최종 확인해야 한다고 안내.
- 불필요한 예약 유도를 지양.

### 5.5 FR-05 상품 큐레이션/비교 (P1, 미구현 또는 기초 구현)

- 카테고리: 통신, 공항 이동, 서울 체험.
- 각 카드의 필드: 공급사, 상품명, 목적, 적합 고객, 가격 표기 유형, 장단점, 제약, 검증일, 구매 CTA.
- 비교는 같은 조건(예: 동일 목적지/일수/데이터량)에서만 수행.
- 가격을 취득한 날짜와 통화, 필수 세금·조건을 표시하거나 가격 대신 공급사 확인 링크 사용.
- 특정 공급사의 높은 수수료가 최상단 추천 근거가 되어서는 안 됨.
- 구매 우선순위는 정확성 → 고객 적합성 → 정책/환불 → 총비용 → 서비스 품질 → 상업 조건 순.
- 상품 공급사 동의 없는 상표 사용·후기 복제 금지.

### 5.6 FR-06 제휴 링크 라우팅 (P0, 부분 구현)

현행 데이터 형태:

```js
window.SEOUL_READY_PARTNERS = {
  airalo: {official: "https://www.airalo.com/south-korea-esim", affiliate: ""},
  viator: {official: "https://www.viator.com/Seoul/d973-ttd", affiliate: ""},
  systeme: {official: "https://systeme.io/", affiliate: ""}
};
```

운영 규칙:
- `affiliate`가 비어 있으면 `official`로 이동.
- `affiliate`에는 해당 계정 대시보드에서 발급받은 URL만 입력.
- 공식적으로 허용된 도메인/HTTPS/프로그램 링크 규정 검증.
- 제휴 링크에 `rel="sponsored noopener noreferrer"` 사용.
- 외부 링크 클릭 전 소비자가 상업적 제휴 사실을 인지할 수 있어야 함.
- 제휴 링크는 상품·국가·지역별 제한을 위반하지 않도록 검토.
- 수익 발생 여부는 프런트엔드 링크 존재가 아니라 공급사 적격 거래 보고로 판정.
- 여행과 무관한 `systeme` 설정은 현재 페이지의 판매 CTA로 사용하지 않는다.

**인수 기준**
- 링크가 비어 있으면 비제휴 공식 링크로 이동.
- 승인 링크 입력 시 정확한 제휴 목적지로 이동.
- 잘못된/비HTTPS 링크는 배포 전 실패시키거나 사용하지 않음.
- 모든 외부 링크가 최신인지 정기 확인.
- 쿠키·어트리뷰션의 동작을 플랫폼이 보장하지 않는다는 점 문서화.

### 5.7 FR-07 제휴/광고 고지 (P0, 구현)

- 구매 링크가 외부 서비스로 연결된다는 점 명시.
- 제휴 링크 활성화 시 수수료 발생 가능성을 눈에 띄게 고지.
- 회사가 상품의 판매자·여행 예약 제공자가 아니라는 점 구분.
- 현재 제휴가 비활성화된 상태를 잘못 '승인 파트너'로 표시하지 않음.
- 기기·브라우저·국가·상품 정책에 따른 제약 고지.
- 고지문은 사이트 운영 실태와 일치해야 하며, 광고 파트너/추적 방식 변경 시 업데이트.

### 5.8 FR-08 콘텐츠 검색 및 SEO (P0/P1)

**P0**
- 고유 title/meta description/semantic heading.
- 안내문, 본문, 관련 가이드 간 내부 링크.
- robots.txt, 검색 색인 허용 여부 확인.
- XML sitemap 및 canonical URL 추가(출시 후 즉시 권장).
- hreflang은 실제 다국어 콘텐츠를 운영할 때만 적용.
- 구조화 데이터는 콘텐츠와 실제 일치하는 유형만 사용.

**P1**
- 검색 의도 기반 콘텐츠 클러스터: 'Korea eSIM', 'Incheon airport arrival', 'Seoul 48 hours', 'phone number for tourists'.
- 저품질 자동 생성·콘텐츠 도배 금지.
- 외부 공식 자료 출처, 실질 비교 항목, 변경 이력 표시.
- 검색 콘솔의 색인/검색어/클릭 데이터 기반 업데이트.

### 5.9 FR-09 접근성/모바일 (P0)

- WCAG 2.2 AA를 설계 목표로 설정(인증·달성 주장 아님).
- 의미 있는 구조, alt/aria, 초점 표시, Skip to content.
- 키보드 탐색 및 메뉴 닫기/열기 상태 정확.
- reduced motion 선호를 존중.
- 색 대비, 입력 레이블, 오류 안내, 작은 화면 터치 영역 점검.
- 느린 모바일 네트워크에서도 주요 글과 링크에 접근 가능.

### 5.10 FR-10 분석·이벤트 (P1, 미구현)

초기에는 개인정보 최소화가 우선. 분석 도구 도입 전 관련 국가의 쿠키/동의 의무를 검토한다.
- `page_view`: page_path, referrer_category, device_category, timestamp_day.
- `planner_start`: source_page.
- `planner_complete`: duration_bucket, interest_category. 개인 식별값 없이 집계.
- `guide_read`: guide_slug, completion_bucket (측정 방식 공개).
- `affiliate_click`: provider_id, product_category, content_id, placement_id, link_status.
- `affiliate_purchase_report`: merchant_report_date, provider_id, campaign/subid, approved_transactions, commission_amount (공급사 보고).
- `affiliate_payout`: currency, amount, received_date, provider_id (관리자 내부 데이터).

**금지:** 신용카드/여권/정밀 위치/건강정보 수집, 비동의 추적, 개인별 여행 습관 판매.

### 5.11 FR-11 피드백/정보 정정 (P1)

- "정보가 오래됨/링크가 작동하지 않음" 신고 채널.
- 이메일 또는 개인정보를 받는 폼을 쓸 경우 처리 목적/보관기간/삭제 절차 명시.
- 정정 접수 → 확인 → 업데이트 → 변경일 기록.
- 이용 후기나 만족도 수치를 실제 수집 없이 생성하지 않음.

### 5.12 FR-12 다국어/목적지 확장 (P2)

- 초기 영어 단일 사이트 유지.
- 성과 있는 시장에서 일본어·중국어 번체·스페인어 중 1개만 테스트.
- 자동 번역만으로 현지 규정, 교통, 가격 정보를 보장하지 않음.
- 서울 외 목적지 확장 전 현지 정보의 검증·운영 책임자 정의.

## 7. 콘텐츠·상품 데이터 모델

정적 JSON/JS 모델로 시작하되 향후 CMS/API로 옮기기 쉽게 ID를 분리한다.

### 7.1 개념 엔티티

- `ContentPage`: id, slug, title, intent, audience, locale, published_at, updated_at, verified_at, source_urls[], status, owner.
- `Provider`: id, brand, official_url, affiliate_program_url, status, approval_date, market_restrictions[], payment_rules, policy_checked_at.
- `ProductOffer`: id, provider_id, category, destination, headline, benefits[], caveats[], eligibility[], official_url, affiliate_url, link_validated_at.
- `Placement`: id, content_id, product_offer_id, position, label, disclosure_flag, status.
- `ClickAggregate`: date, content_id, placement_id, provider_id, count, source_bucket (동의·집계 조건 충족 시).
- `PartnerConversion`: provider_id, report_period, tracking_subid, pending_count, approved_count, rejected_count, currency, approved_commission.
- `Payout`: provider_id, payout_id, currency, amount, paid_at, invoice_reference, reconciliation_status.
- `SourceVerification`: entity_id, original_url, checked_at, verified_fields[], changed_fields[], reviewer.
- `Experiment`: id, hypothesis_id, variants, start/end, sample_size, guardrails, decision.

```json
  "provider_id": "airalo",
  "category": "connectivity",
  "destination": "KR",
  "official_url": "https://www.airalo.com/south-korea-esim",
  "affiliate_url": null,
  "verification_status": "official_link_only",
  "verified_at": null,
  "eligibility_notes": ["Check eSIM support", "Confirm carrier unlock"],
  "commercial_terms_source": "provider dashboard after approval"
}
```

### 7.3 상태 모델

**Provider:** candidate → applied → approved / rejected → active → paused / terminated.  
**Offer:** draft → fact_check → approved_for_publication → live → needs_review → retired.  
**Commission:** referred_click → merchant_pending → merchant_approved / rejected → payable → paid → reconciled.

상태 전이는 내부 운영 문서에 기록하며, 브라우저 이벤트가 단독으로 "구매 완료"를 확정할 수 없다.

## 8. 수익 모델과 유닛 이코노믹스

### 8.1 Affiliate 수익

- 구매가 공급사 웹사이트에서 이루어지고, 수수료·어트리뷰션·환불/취소·쿠키 기간은 공급사 정책에 따름.
- 대표 후보: Airalo(eSIM), Viator(체험). Saily·Klook은 가입 승인과 판매 조건 확인 후 확장.
- 정산 통화, 최소 지급금, 수수료 확정 지연, 실제 입금액을 별도 추적.
- 명시적 승인 없이 제휴 링크 또는 브랜드 관계를 허위로 표시하지 않음.

### 8.2 리셀러/화이트라벨 전환

**검토 시점:** 구매 거래와 고객 수요의 재현성이 검증되고 공급사가 프로그램을 정식 허용할 때.

추가 검증 항목:
- 직접 결제 주체, 판매자 표시, 세금·VAT, 환불 의무, CS 수준.
- API 비용·최소 구매량·재고/가격 동기화·SLA.
- 매입/판매 마진과 카드 수수료, 환불·부정거래 리스크.
- 고객정보 보관 및 규제 의무 증가.
- 공급사 종속성·가격 통제권·계약 해지 조건.

### 8.3 수익 계산식

```text
유효 판매수 = 유입 세션 × 제휴 CTA 클릭률 × 공급사 유효구매율
총 승인 커미션 = Σ(승인 거래별 실제 커미션)
매출 기여도 = 승인 커미션 - 유입비 - 콘텐츠 제작/운영비 - 정산/환전비
실제 현금유입 = 해당 기간 입금된 순 정산액
EPC = 승인 커미션 / 제휴 링크 클릭수
Revenue per 1K Sessions = 승인 커미션 / 세션수 × 1,000
```

**주의:** 클릭률·구매율은 가정값으로 모델링할 수 있지만 실적처럼 표시하지 않는다. 미확정 거래·매출·현금은 구별한다.

### 8.4 실험 기준값(가설, 확정 목표 아님)

| 항목 | 초기 탐색 기준 | 판단 |
|---|---|---|
| 제휴 링크 검증 | 승인된 링크 2개 이상 또는 승인 지연 사유 문서화 | 가입/링크 장애 제거 |
| 데이터 충분성 | 가이드별 최소 100개 이상의 유효 세션을 목표로 수집 | 그 미만은 방향성 위주 해석 |
| 구매 신호 | 승인 거래 1건 또는 공급사 보고 가능한 유효 구매 의도 | 다음 실험 후보 선정 |
| 콘텐츠 품질 | 중요 사실 오류 0건, 깨진 핵심 링크 0건 | 오류 시 배포 중단·수정 |
| 경제성 | 적격 커미션의 증가 추세 및 비용 대비 손익 | 유료 광고 전 필수 확인 |

100세션도 전환율을 안정적으로 판단하기에는 작은 표본이다. 작은 표본에 높은 통계적 확신을 부여하지 않는다.

## 10. 분석·실험 계획

### 10.1 퍼널

`landing → guide_open / planner_start → planner_complete → affiliate_click → merchant_purchase_pending → approved_commission → payout_received`

각 단계의 누락·불확실성 구분:
- `affiliate_click`은 판매가 아니다.
- 공급사 보고에서 거래가 확인되지 않으면 `purchase`를 확정하지 않는다.
- 추적 제한이나 반품으로 공급사 수치와 자사 클릭 수는 일치하지 않을 수 있다.

### 10.2 대시보드 최소 항목

- 일·주·월 방문 세션(정책에 맞는 측정 수단 확보 시).
- 콘텐츠별 이탈/스크롤/CTA 클릭(허용 범위).
- 공급사별 클릭·승인 거래·승인 커미션.
- 미확정/거절/환불 거래 수.
- 실제 입금일과 통화·환율·수수료.
- 30/90일 콘텐츠 운영비·현금 기여.

### 10.3 실험 백로그

| 테스트 | 가설 | 대조/변형 | 성공 지표 | 보호지표 |
|---|---|---|---|---|
| E01 | 체크리스트가 단순 상품 카드보다 유용하다 | 일반 카드 vs 체크리스트 | 적격 클릭 비중 | 안내 정확성 |
| E02 | eSIM 지원 확인 CTA가 구매 CTA보다 신뢰를 높인다 | Buy vs Check compatibility | 가이드 완료/클릭 | 오구매 불만 |
| E03 | 48시간 체험 큐레이션이 맥락 없는 투어 나열보다 낫다 | 목록 vs 일정 맥락 | 체험 클릭→승인 구매 | 과잉 예약 권유 |

트래픽이 적으면 동시 A/B보다 정성 피드백과 순차 실험을 우선한다. 외부 요인 차이를 기록한다.

## 11. 비기능 요구사항(NFR)

### 11.1 성능

### 11.2 안정성

- `main` 푸시 → GitHub Actions 빌드/검증 → Pages 배포.
- 배포 실패 시 해당 커밋과 로그 확인, 이전 정상 버전으로 복원.

### 11.3 보안

- 사이트 소스에 관리자 비밀번호·API Secret·실제 개인정보 저장 금지.

- 현재 서버·DB·폼·쿠키 추적 없이 동작하는 정적 정보 서비스.

## 12. 기술 아키텍처와 운영

### 12.1 현행 아키텍처

```text
GitHub repository
  ├── index.html
  ├── guides/*.html
  ├── disclosure.html
  ├── assets/styles.css
  ├── assets/site.js
  ├── assets/partners.js
  ├── robots.txt
  └── .github/workflows/deploy.yml
          │ push(main)
          ▼
GitHub Actions
          │ static artifact
          ▼
GitHub Pages
          │
          ├── content read / local planner logic
          └── outbound official or approved affiliate link
                             │
                             ▼
                    Supplier checkout
                             │
                             ▼
                  Supplier partner dashboard
```

### 12.2 기술 의사결정

- **유지:** 정적 HTML/CSS/JS + GitHub Pages. 개발비·인프라비가 매우 낮고 현재 요구에는 충분하다.
- **보류:** React/Next.js 전환, 자체 CMS, 검색 DB, 회원가입, 구매 API. 실측 요구가 없는데 추가하면 운영 복잡도만 증가한다.
- **P1 이후 선택:** 콘텐츠가 많아지면 정적 사이트 생성기 또는 Headless CMS 검토.
- **측정:** 개인정보 최소 수집형 분석 도구 우선 검토. 동의 요건을 먼저 충족.
- **파트너 실적:** CSV 다운로드/대시보드 기반 수동 집계부터 시작, 데이터 규모가 커지면 공식 API 연동.

### 12.3 개발·배포 워크플로

1. Issue에 변경 목적·사용자 가치·위험 기록.
2. 별도 브랜치에서 수정 후 PR.
3. 정적 파일 검증(경로, HTML, 링크, 스크립트 구문, 고지).
4. 사실·가격·제휴 조건 검수.
5. main 병합 → Actions 배포 확인 → 사이트 실기기 검증.
6. 배포 SHA/검증일/변경 이유를 릴리스 로그에 기록.

### 12.4 파일별 운영 권한

- `assets/partners.js`: 승인 제휴 링크 설정. 임의 변경 금지, 담당자 승인 필요.
- `index.html`, `guides/`: 편집·출처 관리.
- `disclosure.html`: 추적·제휴 상태 변경 시 필수 동시 검토.
- `.github/workflows/deploy.yml`: 배포 자동화. 권한 및 Actions 버전 점검.
- `README.md`: 기술 운영·배포 설명. 실제 GitHub Actions 방식과 일치하도록 업데이트 필요.
